# Especificação Técnica — E-commerce de Joias

Documento de referência para desenvolvimento. Stack: MySQL (HeidiSQL), pagamento via EFI, telas prototipadas no Figma.

---

# 1. REGRAS DE NEGÓCIO

## 1.1 Carrinho e Autenticação

1. O usuário pode navegar, buscar e adicionar produtos ao carrinho **sem estar logado**.
2. O carrinho anônimo é identificado por um `session_token` (UUID) gravado em cookie `HttpOnly`, validade de 30 dias.
3. O login é **obrigatório apenas no momento do checkout** (ao clicar em "Finalizar compra").
4. Ao fazer login, se o usuário já possuía um carrinho salvo no banco, os dois carrinhos são **mesclados**:
   - Produto presente apenas no carrinho anônimo → é adicionado.
   - Produto presente apenas no carrinho do usuário → é mantido.
   - Produto presente nos dois → as quantidades são **somadas**.
   - Se a soma ultrapassar o estoque disponível, a quantidade é limitada ao estoque e o usuário é avisado.
   - O `preco_unitario` mantido é o do carrinho do usuário logado (o mais antigo).
5. Após a mesclagem, o carrinho anônimo é marcado com `deleted_at` e o cookie de sessão é descartado.
6. O carrinho do usuário logado é **persistente**: permanece salvo até que ele remova o item manualmente ou finalize a compra.
7. Ao finalizar a compra com sucesso, os itens do carrinho são convertidos em `order_items` e o carrinho é esvaziado.

## 1.2 Estoque e Disponibilidade

8. O estoque é controlado **por variação** (`product_variants.stock_quantity`), não por produto.
9. Um produto só é exibido ao usuário comum se: `active = 1` **E** `deleted_at IS NULL` **E** possui ao menos uma variação com `stock_disponivel > 0`.
10. Uma variação com estoque zero não é selecionável na página de produto (aparece riscada / desabilitada).
11. Se um item já está no carrinho e o estoque acaba, o item **não é removido silenciosamente**:
    - Permanece visível no carrinho com o rótulo **"Indisponível"**.
    - Fica visualmente esmaecido e com a quantidade bloqueada.
    - O botão de checkout é desabilitado enquanto houver item indisponível.
    - O usuário deve remover manualmente ou usar o botão "Remover indisponíveis".
12. Se o estoque diminuiu mas ainda existe (ex.: usuário tem 5, restam 2), o carrinho exibe: "Restam apenas 2 unidades" e ajusta automaticamente a quantidade.
13. O estoque é revalidado em **três momentos**: ao abrir o carrinho, ao iniciar o checkout e imediatamente antes de gerar a cobrança.

## 1.3 Reserva de Estoque (TTL)

14. Ao iniciar o checkout, o sistema cria registros em `stock_reservations` para cada item.
15. A reserva tem validade de **20 minutos** (`expires_at`).
16. O estoque disponível para venda é calculado como:
    ```
    disponivel = stock_quantity - SUM(reservas ativas e não expiradas de outros usuários)
    ```
17. A reserva é liberada quando:
    - O pagamento é confirmado (converte-se em baixa definitiva de estoque).
    - O prazo de 20 minutos expira.
    - O usuário cancela o checkout ou volta ao carrinho.
    - O pagamento é recusado ou expirado.
18. Um **job agendado (cron)** roda a cada 2 minutos liberando reservas expiradas e cancelando pedidos vencidos.
19. Se durante o checkout um item perder a reserva (concorrência), o usuário é devolvido ao carrinho com aviso claro.

## 1.4 Preços

20. O `preco_unitario` é **congelado** no momento em que o produto entra no carrinho.
21. Se o admin alterar o preço, carrinhos existentes **não são alterados**.
22. Regra de segurança: se o preço congelado for **maior** que o preço atual, o sistema usa o preço atual (favorece o cliente).
23. Ao gerar o pedido, todos os dados são copiados como **snapshot** em `order_items`: nome, preço, SKU, variação. O pedido nunca depende de JOIN com a tabela de produtos para exibir histórico.

## 1.5 Exclusão (Soft Delete)

24. **Nenhum registro é excluído fisicamente.** Todas as tabelas de domínio possuem `deleted_at DATETIME NULL`.
25. Um produto com `deleted_at` preenchido comporta-se exatamente como estoque zero: some das listagens e fica "Indisponível" nos carrinhos.
26. Produtos referenciados em pedidos históricos nunca são removidos do banco.
27. Todas as queries de listagem pública incluem obrigatoriamente `WHERE deleted_at IS NULL`.
28. O painel admin possui uma visão "Lixeira" com opção de restaurar.

## 1.6 Cupons e Frete

29. Frete grátis automático para subtotal igual ou superior a **R$ 219,00** (valor configurável).
30. Cupom aplicado sobre o subtotal, antes do frete.
31. Regras do cupom: código único, tipo (percentual ou valor fixo), valor mínimo de compra, data de validade, limite total de usos e limite por usuário.
32. Um pedido aceita **apenas um cupom** por vez.
33. Cupons não são cumulativos com outras promoções de mesmo tipo.

# 3. MÁQUINA DE ESTADOS DO PEDIDO

```
                    ┌──────────────┐
                    │   pendente   │  (carrinho virou pedido)
                    └──────┬───────┘
                           ▼
              ┌────────────────────────┐
              │ aguardando_pagamento   │  (cobrança gerada na EFI)
              └──┬─────────┬───────────┘
                 │         │
        (webhook)│         │(TTL 20min ou recusa)
                 ▼         ▼
            ┌────────┐  ┌─────────────────────┐
            │  pago  │  │ expirado/cancelado  │
            └───┬────┘  └─────────────────────┘
                ▼              (libera reserva)
          ┌───────────┐
          │ separando │
          └─────┬─────┘
                ▼
          ┌──────────┐
          │ enviado  │  (tracking_code preenchido)
          └────┬─────┘
               ▼
         ┌───────────┐
         │ entregue  │
         └───────────┘

Ramo alternativo a partir de "pago":
   pago → estornado  (devolve estoque + registra stock_movement)
```

Transições permitidas — qualquer outra deve ser rejeitada pela aplicação:

| De | Para |
|---|---|
| pendente | aguardando_pagamento, cancelado |
| aguardando_pagamento | pago, expirado, cancelado |
| pago | separando, estornado |
| separando | enviado, estornado |
| enviado | entregue |
| entregue | (final) |

# 4. INTEGRAÇÃO EFI

## 4.1 Configuração inicial

1. Criar conta na EFI e gerar aplicação no painel.
2. Obter `client_id` e `client_secret` — **um par para produção, outro para homologação**.
3. Baixar o **certificado `.p12`** e armazená-lo **fora da pasta pública** (ex.: `storage/certs/`).
4. Configurar `.env`:
   ```
   EFI_CLIENT_ID=
   EFI_CLIENT_SECRET=
   EFI_CERTIFICATE_PATH=storage/certs/producao.p12
   EFI_SANDBOX=true
   EFI_PIX_KEY=
   EFI_WEBHOOK_URL=https://seudominio.com/webhook/efi
   ```
5. Adicionar `*.p12` ao `.gitignore`.

## 4.2 Fluxo Pix

1. Cliente conclui o checkout.
2. Backend valida estoque, cria o pedido com status `pendente` e cria as reservas.
3. Backend autentica na EFI (OAuth com certificado) e obtém o access token.
4. Cria cobrança imediata (`PUT /v2/cob/{txid}`) com valor, chave Pix e expiração de 1200 segundos.
5. Gera o QR Code (`GET /v2/loc/{id}/qrcode`).
6. Salva `txid`, `qr_code` e `copia_e_cola` na tabela `payments`.
7. Pedido passa para `aguardando_pagamento`.
8. Tela exibe QR Code + código copia-e-cola + contador regressivo.
9. Frontend faz polling a cada 5 segundos consultando o status local do pedido.
10. EFI envia webhook ao confirmar o pagamento.
11. Backend valida o webhook, marca o pagamento como aprovado, baixa o estoque e envia e-mail de confirmação.

## 4.3 Webhook — requisitos obrigatórios

12. A URL precisa ser **HTTPS pública e válida**. Não funciona em `localhost` — usar **ngrok** durante o desenvolvimento.
13. O endpoint precisa aceitar **mTLS** (a EFI envia certificado cliente). Configurar no Nginx/Apache.
14. Registrar o webhook uma vez via API (`PUT /v2/webhook/{chave}`).
15. O handler deve ser **idempotente**: verificar se o `txid` já foi processado antes de baixar estoque. Reprocessar não pode zerar o estoque.
16. Responder **HTTP 200** sempre e rapidamente. Processamento pesado vai para fila.
17. Registrar o payload bruto em `payments.raw_response` para auditoria.
18. Como redundância, criar um job que consulta pedidos `aguardando_pagamento` com mais de 3 minutos e verifica o status diretamente na API.

## 4.4 Cartão de crédito

19. Usar o **SDK JavaScript da EFI** para tokenizar o cartão no navegador.
20. O número do cartão **nunca** trafega pelo seu servidor — apenas o `payment_token`.
21. Enviar ao backend: token, parcelas, dados do titular e endereço de cobrança.
22. Backend cria a cobrança (`POST /v1/charge/one-step`).
23. Tratar retornos: aprovado, recusado, em análise.
24. Configurar o número máximo de parcelas e o valor mínimo por parcela.

## 4.5 Regras de segurança

25. Nunca confiar no retorno do frontend para confirmar pagamento. Só o webhook (ou consulta ativa) confirma.
26. Validar o valor recebido contra o valor do pedido antes de aprovar.
27. Renovar o access token respeitando a expiração (cache com margem de segurança).
28. Registrar todas as chamadas à EFI em log para depuração.

# 8. REQUISITOS TÉCNICOS E NÃO-FUNCIONAIS

## 8.1 Segurança

1. Senhas com hash bcrypt ou Argon2 — nunca MD5 ou SHA1.
2. Proteção CSRF em todos os formulários.
3. Prepared statements em todas as queries (proteção contra SQL Injection).
4. Escape de saída em todo conteúdo dinâmico (proteção contra XSS).
5. Rate limiting no login (máximo 5 tentativas por 15 minutos).
6. Rate limiting na aplicação de cupons.
7. HTTPS obrigatório em produção com redirecionamento de HTTP.
8. Cookies com flags `HttpOnly`, `Secure` e `SameSite=Lax`.
9. Validação de dados tanto no frontend quanto no backend.
10. Certificado da EFI fora do diretório público e fora do versionamento.
11. Upload de imagem: validar tipo MIME real, extensão e tamanho máximo (5 MB).
12. Renomear arquivos enviados com hash — nunca preservar o nome original.

## 8.2 Performance

13. Índices em todas as colunas usadas em `WHERE` e `JOIN`.
14. Imagens convertidas para WebP com múltiplos tamanhos (thumb, médio, grande).
15. Lazy loading nas imagens de listagem.
16. Cache de categorias e configurações.
17. Paginação obrigatória — nunca carregar todos os produtos.
18. Compressão gzip/brotli ativada.

## 8.3 Integridade

19. Transações SQL em: criação de pedido, baixa de estoque e mesclagem de carrinho.
20. Uso de `SELECT ... FOR UPDATE` ao decrementar estoque, evitando corrida.
21. Constraints de chave estrangeira ativas com `ON DELETE RESTRICT`.
22. Backup automático diário do banco.

## 8.4 Jobs agendados (cron)

23. A cada 2 minutos: liberar reservas expiradas.
24. A cada 5 minutos: consultar status de pagamentos pendentes na EFI (redundância do webhook).
25. Diário: marcar carrinhos abandonados com mais de 30 dias.
26. Diário: backup do banco de dados.
27. Semanal: relatório de estoque baixo por e-mail.

## 8.5 LGPD e legal

28. Política de Privacidade e Termos de Uso publicados.
29. Banner de consentimento de cookies.

# 10. PONTOS QUE AINDA PRECISAM DE DECISÃO

1. **Linguagem/framework do backend** — PHP puro, Laravel, Node? (você citou o StockSys como referência)
2. **Frete** — tabela fixa por faixa de CEP, API dos Correios ou Melhor Envio?
3. **Hospedagem** — precisa suportar HTTPS válido, cron e mTLS no webhook
4. **Onde ficam as imagens** — disco local do servidor ou storage externo (S3, Cloudflare R2)?
5. **Envio de e-mail** — SMTP próprio ou serviço (Resend, SendGrid, Mailgun)?
6. **Compra como visitante** — a regra atual exige login no checkout. Confirmar que não haverá guest checkout
7. **Estorno e devolução** — processo manual pelo admin ou automatizado via API da EFI?
8. **Múltiplos administradores** — haverá níveis diferentes de permissão ou todo admin pode tudo?
